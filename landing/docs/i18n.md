# Landing i18n architecture

How the landing site (Vite + React Router + react-i18next, SSR-prerendered) serves five languages while keeping the eager entry chunk small and avoiding soft-404 links to untranslated content.

## Supported languages

Five locales, declared in `landing/src/i18n.ts`:

```
en  es  ru  uk  zh   (SUPPORTED_LANGS)
```

- **`en` is the source / default** (`lng: 'en'`, `fallbackLng: 'en'`, `defaultNS: 'home'`). EN lives on the bare root (`/`, `/about`, …); every other language is path-prefixed (`/ru`, `/ru/about`, …).
- `LANG_LABELS` (`EN`/`ES`/…) drives the switcher UI; `OG_LOCALES` maps each to a BCP-47 underscore form (`en_US`, `ru_RU`, `uk_UA`, `zh_CN`) for `og:locale` meta.

Translation bundles live under `landing/public/locales/<lang>/<namespace>.json`. All five languages currently carry the same 15 on-disk namespaces: `about, articles, bio, bio-metric, contact, emoton, glossary, home, inner-spectrum, level, part, privacy, reviews, sitemap, terms` (`home.json` is required; others fall back to EN per-key when missing).

> Note: the `ns` array in `i18n.init()` (`landing/src/i18n.ts`) is the registry of namespace names, not a guarantee every file exists in every language. Missing files fall back to the EN bundle (see `ensureNamespace`'s `.catch`).

## Lazy per-namespace loading

Only the **`home`** namespace ships in the eager entry chunk. It is statically imported for all five languages at the top of `landing/src/i18n.ts`:

```ts
import en from '../public/locales/en/home.json'   // + es/ru/uk/zh
resources: { en: { home: en }, es: { home: es }, … }
```

Every other namespace (`about`, `bio`, `glossary`, `articles`, `reviews`, …) is **excluded from the bundle** and loaded on demand by `ensureNamespace(lng, ns)`:

- It `import()`s `../public/locales/<l>/<ns>.json` (Vite emits one cacheable chunk per file) and registers it with `i18n.addResourceBundle`.
- It loads the requested language **plus the `en` fallback** (for non-EN langs), so a partially-translated namespace still renders sensible text.
- Results are memoised in a `Map` keyed `"<lang>:<ns>"` — each language/namespace pair is fetched at most once.
- A missing locale file is swallowed (`.catch`) so i18next falls back to the EN bundle rather than throwing.

**Why:** keeping only `home` eager guards the entry-chunk gzip budget. Layout nav + the homepage need `home`; bundling the dozen other namespaces (and ×5 languages) into the entry chunk would bloat first paint. See the header comment in `landing/src/i18n.ts`.

The client wiring is in `landing/src/main.tsx`: the `lazyNs(ns, load)` helper wraps `React.lazy` so the route factory resolves the page chunk **and** `ensureNamespace(lang, ns)` together before mounting. React holds the prerendered HTML behind `<Suspense>` until both resolve — no hydration mismatch, no flash of raw translation keys. Pages without translated copy (e.g. all `/tools/*`, `/topics`, `/research`) use plain `lazy()` with no namespace.

On `languageChanged`, an i18next listener (`landing/src/i18n.ts`) re-fetches every already-loaded namespace in the new language so SPA navigation after a switch is populated.

## Localized routes & hreflang

URL generation per language lives in `landing/src/i18n.ts`:

- `homePathFor(lang)` → `/` for EN, `/<lang>` otherwise.
- `langHref(path, lang)` — the function every internal `<Link to>` / markdown link must pass through. EN returns the path unchanged; otherwise it prefixes `/<lang>`. It is idempotent and skips already-prefixed paths and `NON_LOCALIZED_PREFIXES` (`/the-stack`, `/topics`, `/tools`, `/research` — EN-only sections). It also consults `LOCALIZED_COVERAGE` for partially-localized content (see below).
- `localizedPathFor(pathname, lang)` — drives the language switcher; preserves the slug across switches for `/bio/:metric`, `/level/:n`, `/part/:slug`, `/articles/:slug`, `/glossary/:slug`, and nested `/reviews/...`, falling back to EN where no localized page exists.
- `LOCALIZED_PAGES` is the registry of fully-localized base paths (`/`, `/about`, `/articles`, `/bio`, `/contact`, `/emoton`, `/inner-spectrum`, `/privacy`, `/sitemap`, `/terms`) → namespace. `localizedRouteVariants()` expands these for the prerender; `metricRouteVariants` / `levelRouteVariants` / `partRouteVariants` do the same for detail pages.

Both routers (`landing/src/main.tsx` client, `landing/src/entry-server.tsx` SSR) register the EN route plus a `/<lang>/...` variant for each non-EN language via `SUPPORTED_LANGS.filter(l => l !== 'en').map(...)`.

**hreflang** is emitted at prerender time by `landing/scripts/prerender.ts` (not at runtime). `buildHreflangLinksFor*` helpers write `<link rel="alternate" hreflang="<lang>">` for each language plus `hreflang="x-default"` → the EN URL. EN pages whose slug has a localized sibling also emit the cluster from the EN side. Pages that received no cluster get a self-referencing `hreflang="en"` + `x-default` fallback (gated on the absence of any existing `hreflang=`). `og:locale` / `og:locale:alternate` are injected here for prerendered pages and re-synced client-side by `syncOgLocale(lang)` in `landing/src/utils/ogLocale.ts`.

## localized-coverage — avoiding soft-404s

Articles, glossary terms, and reviews are only **partially** localized (drip/pilot rollout) — not every slug exists in every language. Linking `/ru/articles/<slug>` to a slug with no RU prerender would produce a soft-404 (HTTP 404 + SPA shell).

`langHref` (and `localizedPathFor`) guard against this by consulting **`LOCALIZED_COVERAGE`** from `landing/src/data/localized-coverage.generated.ts`:

```ts
LOCALIZED_COVERAGE[lang] = { articles: Set<slug>, glossary: Set<slug>, reviews: Set<remainder> }
```

If the active locale's set does not contain the slug, `langHref` returns the **bare EN path** instead of a `/<lang>/...` link. (For reviews the key is the full remainder after `reviews`, where `''` = the index; for glossary the bare index also falls back when the locale has zero glossary slugs.)

The set is **generated**, not hand-maintained, by `landing/scripts/generate-localized-coverage.ts`:

- It reads `LOCALIZED_ARTICLE_ROUTE_SET`, `LOCALIZED_GLOSSARY_ROUTE_SET`, `LOCALIZED_REVIEW_ROUTE_SET` from `landing/scripts/prerender-routes.ts` — the **same route sets the prerender uses** — so the link-fallback logic and the actually-prerendered pages can never drift.
- It buckets slugs by language (`es`/`ru`/`uk`/`zh`; EN needs no coverage gate) and writes the `Set`-based module. The file header marks it auto-generated — do not edit by hand; re-run the script after changing which slugs are localized.

(Current state in the committed file: ES has ~22 localized articles, RU ~13, UK/ZH 0 articles; reviews are broadly localized for ES/RU/UK, none for ZH; glossary detail pages are 0 across all locales.)

## SSR vs client i18n

- **SSR / prerender** (`landing/src/entry-server.tsx`): all page components are **static imports** (`renderToString` cannot use `React.lazy`). The heavy/lazy namespaces are deliberately **not** imported here; instead `landing/scripts/prerender.ts` walks `landing/public/locales/` and registers every `<lang>/<ns>.json` on the shared i18n instance via `addResourceBundle` **before** any `renderToString` call. `createApp(location, lang)` synchronously sets `i18n.changeLanguage` so the rendered HTML is already translated.
- **Client** (`landing/src/main.tsx`): page components and namespaces are both **lazy**. `i18n.changeLanguage(langFromPath(window.location.pathname))` runs before hydration so first paint matches the prerendered HTML; `lazyNs` then loads each namespace on demand.

The single shared `i18n` instance (`react: { useSuspense: false }`, `initImmediate: false`) is used by both paths.

## Adding a namespace / keeping languages in parity

To add a fully-localized page:

1. Add the entry to `LOCALIZED_PAGES` in `landing/src/i18n.ts` (base path → namespace).
2. Create `landing/public/locales/<lang>/<ns>.json` for each language.
3. Register the namespace name in the `ns` array of `i18n.init()`.
4. Wire the route with `lazyNs('<ns>', …)` in `landing/src/main.tsx` and a static import + route in `landing/src/entry-server.tsx` (both with the per-language variant loop).
5. Add a meta override + hreflang in `landing/scripts/prerender.ts`.

To localize more article/glossary/review slugs: add them to the route sets in `landing/scripts/prerender-routes.ts`, then re-run `landing/scripts/generate-localized-coverage.ts` to refresh the coverage module.

**Parity tooling caveat:** the app-side scripts `scripts/i18n-audit.cjs` and `scripts/i18n-quality-en-ru.cjs` exist at the repo root, but they audit the **mobile app's** i18n, which is a **separate** system from this landing i18n. They do not check `landing/public/locales/`. The landing site has no equivalent automated parity audit — missing keys silently fall back to EN at runtime.

## Source files

- `landing/src/i18n.ts` — instance init, `SUPPORTED_LANGS`, `ensureNamespace`, `langHref`, `localizedPathFor`, `LOCALIZED_PAGES`, route-variant builders.
- `landing/public/locales/<lang>/<ns>.json` — translation bundles (5 langs × 15 namespaces on disk).
- `landing/src/main.tsx` — client router; `lazyNs` (lazy chunk + lazy namespace).
- `landing/src/entry-server.tsx` — SSR router; static imports, `createApp`.
- `landing/scripts/prerender.ts` — registers all locales for SSR; emits hreflang + og:locale + localized meta.
- `landing/scripts/generate-localized-coverage.ts` — generator for the coverage set.
- `landing/src/data/localized-coverage.generated.ts` — generated per-locale slug sets (do not edit).
- `landing/scripts/prerender-routes.ts` — `LOCALIZED_*_ROUTE_SET` source of truth.
- `landing/src/utils/ogLocale.ts` — client-side `og:locale` sync.
- `landing/src/utils/normalizePath.ts` — trailing-slash normalization for links.
- `landing/src/config/routes.ts` — EN `staticPaths` list.
- `landing/src/components/Layout.tsx` — language switcher + nav (consumes `langHref`/`localizedPathFor`).

## Uncertainties

- The committed coverage counts above reflect a snapshot of `localized-coverage.generated.ts`; treat the generator + route sets as the live source.
- `level` and `part` are passed to `lazyNs` in `main.tsx` and listed in the `ns` registry, but I confirmed on-disk JSON only for the namespaces listed; their `level.json`/`part.json` do exist in each locale dir, but per-key translation completeness across all 5 languages was not exhaustively verified.
- hreflang/meta injection in `prerender.ts` is extensive and branch-heavy; I documented the structure and the x-default/self-referencing fallback, not every per-content-type branch.
