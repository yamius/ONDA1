## Система разблокировки частей (Parts)

**ВАЖНО:** Части разблокируются последовательно после прохождения всех базовых практик предыдущей части.

### Логика разблокировки

- **Part 1** всегда доступна (стартовая часть).
- **Part N** разблокируется только когда пройдены **все практики** Part (N-1).
- Проверка идёт по `practiceHistory` — нужна хотя бы одна сессия для каждой практики предыдущей части.
- Функция проверки: `isPartUnlocked(partNumber)` в `src/onda-level1-demo_27.tsx` (~строка 1848).

### Где применяется проверка

1. **Dropdown для Chapter** (~строка 4468): недоступные главы показываются заблокированными (серые, с 🔒).
2. **Dropdown для Level/Part** (~строка 4627): недоступные части показываются заблокированными (серые, с 🔒).
3. **Кнопка "Go to Part X"** (~строка 5834): кнопка скрывается, если следующая часть не разблокирована.
4. **При загрузке данных пользователя** (~строка 543): если пользователь на недоступной части, автоматически переключается на последнюю доступную.

### Режим разработки

**Для работы со всеми частями во время разработки:**

Создай файл `.env.local` в корне проекта и добавь:
```
VITE_UNLOCK_ALL_PARTS=true
```

После этого все части будут открыты для тестирования.

**Для production:**
- Просто убери переменную `VITE_UNLOCK_ALL_PARTS` (или не добавляй её).
- Проверка разблокировки будет работать автоматически.
- При `npm run build` в production build `import.meta.env.DEV === false`, проверка включится автоматически.

### Технические детали

- Функция `isPartUnlocked` использует `useMemo` и зависит от `circuits` и `practiceHistory`.
- Проверка идёт по ID практик вида `p1-1`, `p2-1`, `p3-1` и т.д.
- Если у предыдущей части нет практик (пустой массив) — следующая часть считается разблокированной.

## Git: Правильный workflow для коммитов и пуша

**⚠️ ВАЖНО: Не ходить кругами! Делай правильно с первого раза.**

### ✅ Правильная последовательность при push:

1. **Проверь статус:**
   ```bash
   git status
   ```

2. **Добавь файлы:**
   ```bash
   git add <файлы>
   # или для всех изменений:
   git add .
   ```

3. **Создай коммит:**
   ```bash
   git commit -m "описание изменений"
   ```

4. **Перед push ВСЕГДА делай pull с rebase:**
   ```bash
   git pull --rebase origin main
   ```
   Это интегрирует удалённые изменения без merge-коммитов.

5. **Затем push:**
   ```bash
   git push origin main
   ```

### ❌ НЕ делай так (лишние шаги):

- ❌ Не делай `git push` без предварительного `git pull --rebase`
- ❌ Не используй `git pull` без `--rebase` (создаёт лишние merge-коммиты)
- ❌ Не пытайся удалять `.git/index.lock` вручную — обычно это не нужно
- ❌ Не делай несколько попыток push подряд — сначала pull

### Если push отклонён (rejected):

**Правильно:**
```bash
git pull --rebase origin main
git push origin main
```

**Неправильно:**
- Делать `git push` несколько раз
- Пытаться удалить lock-файлы
- Использовать `git pull` без `--rebase`

### Одной командой (если уверен, что нет конфликтов):

```bash
git add . && git commit -m "описание" && git pull --rebase origin main && git push origin main
```

Но лучше делать по шагам, чтобы видеть возможные проблемы.

## Build Environment

**ВАЖНО:** У пользователя **НЕТ Mac**. Все iOS сборки происходят через:

1. **GitHub Actions** — автоматическая сборка при push в main
2. **TestFlight** — распространение тестовых сборок
3. **Fastlane** — автоматизация code signing и деплоя

### Что это значит для разработки:

- ❌ Нельзя попросить "запусти `npx cap open ios`" — нет Xcode
- ❌ Нельзя попросить локальную iOS сборку
- ✅ Изменения iOS кода проверяются через CI/CD pipeline
- ✅ После push в main — ждать сборку в GitHub Actions
- ✅ Тестирование на реальном устройстве через TestFlight

### Workflow

1. Cursor/Replit → редактирование кода
2. Git push → GitHub
3. GitHub Actions → автоматическая сборка iOS (Fastlane)
4. TestFlight → установка на iPhone для тестирования

### Native iOS изменения

При изменении Swift кода (`ios/App/`):
- Код попадает в сборку автоматически при следующем push
- Capacitor плагины синхронизируются в CI (`npx cap sync ios`)
- Проверка ошибок компиляции — в логах GitHub Actions
